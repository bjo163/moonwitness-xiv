## Implemented

- Added `@moonwitness/orm-knowledge` as a programmatic addon with three separate records: immutable-source testimony, numbered sourced corrections, and linked interpretations.
- Preserved source text for time, precision, and uncertainty. Each correction carries its own source label, locator, digest, actor, and asserted-time precision.
- Interpretation rows reference an assertion and evidence independently; they do not update or replace the testimony.
- New records default to `RESTRICTED`; generic-user model access is seeded as denied; addon menus are development-only.
- Seeded model-level grants are explicitly false for ordinary users. Separately, the central generic REST/RPC policy hard-denies all three witness models for `user`, `superadmin`, and `system`; role privilege or model grants cannot bypass the dedicated scoped endpoint.
- Testimony now carries an optional `company_id` and an explicit `synthetic` flag that defaults false. Corrections and interpretations also default to `synthetic=false`; the scoped reader requires the testimony, every returned correction, and every returned interpretation to be explicitly synthetic. Unclassified rows are hidden. A new versioned ORM addon seed provides one restricted, owner/company-bound synthetic example and a least-privilege witness-steward group for the seeded superadmin.
- Added read-only `GET /api/research/witnesses/:witnessId`. It derives actor and company from verified request auth, rechecks active superadmin status, active company membership, active witness-steward group membership and active record state in the database, and filters by owner, tenant, restricted visibility and synthetic classification. Inactive corrections and interpretations are omitted. Guessed, wrong-owner, foreign-company and non-synthetic IDs all return the same 404 response. No collection, create, update or delete endpoint is registered; real testimony intake remains disabled.
- Added an upgrade test for a populated 1.3-style witness table: the programmatic schema sync adds the nullable company link and false-by-default synthetic marker without misclassifying or rewriting the legacy row. Only the new scoped fixture carries the default company and explicit synthetic owner binding; pre-existing immutable seeds with null classification remain hidden.
- Added idempotently installed SQLite and PostgreSQL triggers that reject direct SQL `UPDATE` and `DELETE` on testimony, correction, and interpretation tables. The setup runs transactionally after model synchronization, so it covers both fresh installs and existing addon tables.
- Kept the database unique constraint on `(testimony_id, sequence)` and added simultaneous insert tests proving that only one correction can claim a sequence, even when both writes bypass ORM hooks.
- The pre-insert correction helper now scans the full existing sequence chain and rejects every next-sequence request when persisted rows contain a gap. A synthetic fixture inserts sequence 3 after sequence 1 and confirms both sequence 2 and 4 are rejected; no write endpoint or real-data intake is enabled.
- Added `appendOwnedSyntheticWitnessCorrection`, an internal PostgreSQL/SQLite service that rechecks the active superadmin, active company membership and steward group under row locks in the transaction, then locks an owned, active, explicitly synthetic `RESTRICTED` testimony and its full correction chain. It appends only the next contiguous sequence; exact same-owner retries are idempotent, and conflicting payloads, gaps, foreign tenant/owner, inactive or non-synthetic records fail closed. There is no HTTP write route or real-data intake.
- Correction source fields and digest are checked for shape and recorded as attribution metadata. The append now also requires a caller-supplied source resolver that returns verified local bytes, a `permitted` rights state and an explicit `quote_excerpt` allowance for the same label, locator and digest; without a resolver, or with an unverified or mismatched one, both the append and the idempotent replay fail closed. Its fixtures are synthetic.
- Added a JSON Schema contract, a synthetic seed for each record type, ORM and raw-SQL immutability tests, sequence/provenance checks, and workspace addon-conformance registration.

## Correction source verification gate — local `dev` worktree

- `appendOwnedSyntheticWitnessCorrection` now takes an optional `resolveSource` resolver, the same fail-closed shape already used by `storeStoryVersion`. The appended or replayed correction is accepted only when the resolver returns `bytes_verified: true`, `rights_state: 'permitted'` and `quote_excerpt` among `allowed_uses`, for the identical `source_label`, `source_locator` and `source_digest`. A missing resolver, a `null` result, a non-permitted rights state, a missing citation use and a resolver that renames any source field are all rejected before any write, so an idempotent replay is verified exactly like a first append. The owner/company/steward and synthetic-record checks still run first, so a hidden record keeps returning the same not-found error.
- Exported contract types: `WitnessCorrectionSourceReference`, `VerifiedWitnessCorrectionSource`, `WitnessCorrectionSourceResolver`.
- No HTTP write route exists, therefore no production caller supplies a real resolver yet. Wiring one against the owner-approved corpus sample stays behind the same real-data intake gate as the write path itself; the helper no longer treats shape-checked attribution metadata as verified provenance.

## Remaining acceptance and limits

- The scoped reader is deliberately superadmin-steward-only and exposes only synthetic fixtures. It is not the future purpose/consent authorization flow for ordinary witnesses. No list/search, export, public projection, preview, or real-data intake is enabled; a dedicated route returning one record is not proof that all derivative surfaces support withdrawal.
- Database triggers protect against ordinary SQL update/delete paths, but a database owner or privileged operator can alter/drop the triggers or mutate underlying files. This is an integrity guard, not a tamper-proof audit system.
- The internal correction writer is not exposed through HTTP and is restricted to explicitly synthetic `RESTRICTED` records. Do not enable real-data write paths until retention, revocation, downstream invalidation, purpose/consent authorization, and privacy/safeguarding review are accepted and verified.
- Retention, revocation, downstream invalidation, and workflow-specific privacy/safeguarding approval remain K5-002 and owner gates. Keep production and real-data intake disabled until those controls are implemented and independently verified.
