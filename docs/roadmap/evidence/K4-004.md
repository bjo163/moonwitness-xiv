## Profile-digest review binding — 2026-10-25

The `ad84d60` guard is replaced by an actual binding. Nothing here changes the K3 rule that a review event authorizes an exact Assertion revision and can never decide a tenant's profile interpretation; this adds the separate, tenant-local decision that K3-007 left as the missing piece.

- `packages/research/src/concept-profile-review.ts` defines the decision record and its unforgeable brand, following the precedent of `attestedResolutions` in `packages/research/src/evidence.ts` and the `decisionAuthorities` WeakMap in `packages/research/src/identity-reconciliation.ts`. `mintConceptProfileReviewDecision` records the decision in a module-private WeakMap together with the reviewing company and reviewer, so only the object it returns carries authority: a spread clone or a JSON round-trip is structurally identical and unauthorized. Minting refuses a blank or over-long id, a profile id outside `mw:concept-profile:…`, either digest outside 64 lowercase hex, a reviewed version below 1 or not a safe integer, an outcome outside `accepted`/`rejected`, an unparseable `decided_at`, and a blank or over-4000-character rationale. The returned object is frozen.
- `authorizesConceptProfile(decision, companyId, { profile_id, profile_digest })` requires all four of: minted in this company, `outcome === 'accepted'`, same profile identity, same canonical profile digest.
- `validateConceptProfileWithEvidence` accepts an optional trusted context `{ company_id, resolve(profileId) }`. Without it the behavior is exactly `ad84d60`'s — every accepted interpretation stays `profile_review_pending`, and the existing regression asserting that still passes unchanged. With it, a resolver that throws yields `profile_review_resolver_failure`, `null` yields `profile_review_pending`, an object that is not a minted decision for this company yields `profile_review_unattested`, a decision naming another profile yields `profile_review_identity_mismatch`, and a rejecting outcome yields `profile_review_rejected`.
- New append-only table `knowledge_concept_profile_review_decisions` (model `knowledge.concept_profile_review_decision`, addon manifest `1.6.0` → `1.7.0`): company-scoped, unique on `(company, profile_digest, reviewer)`, storing the profile identity and proposal digest, the reviewed version and its digest, the outcome, the reviewer, `decided_at`, and a hidden rationale. Both append-only branches are asserted: SQLite `RAISE(ABORT, 'Concept profile review decisions are append-only')` and the PostgreSQL trigger function.
- `recordConceptProfileReviewDecision(db, …)` runs in one transaction: it rechecks the authenticated user/role/company membership, locks the company row, requires that the reviewed profile version is actually stored, refuses the version's own author as reviewer, re-verifies the stored bytes against `profile_digest`, computes the digest of the _proposed_ accepted document with the store's canonical JSON writer, then inserts. Repeating the same reviewer + same proposal digest is idempotent and returns the same decision; the same pair with a different outcome or a different reviewed version fails, so a reviewer cannot overwrite their own verdict.
- `resolveConceptProfileReviewDecision(db, …)` returns the newest accepted decision for one exact profile identity and digest inside the reader's active company, and it returns null rather than an unauthorized object whenever the reviewed version has gone missing, its stored bytes no longer match `reviewed_digest`, or the reviewer turns out to be the version's author. Every read therefore re-verifies against storage instead of trusting the row.
- `storeConceptProfiles` now permits an `accepted` interpretation only when one of those re-verified decisions binds the exact canonical digest of the profile being submitted. The check runs before evidence resolution, and a refusal writes no version row.
- End-to-end regression in `packages/orm-knowledge/tests/research-review.test.ts`: an accepted K3 Assertion review over real synthetic graph evidence still does not authorize the profile; after a second user records the accepted digest-bound decision, the identical content stores as version 2, and the same profile with one interpretation reworded is refused because its digest no longer matches.

### Boundary this unit does not cross

- Digest equality is enforced where the canonicalizer lives, not inside the pure validator. `packages/research/src/concept-profile.ts` hashes with `stableJson` while `packages/orm-knowledge/src/research-release.ts` writes the persisted digest with `canonicalResearchJson`; they are deliberately not interchangeable, so the research validator cannot recompute a stored profile digest and checks attestation, company, profile identity and outcome only. A caller must therefore pass the store that minted the decision, which is the only component that can bind bytes to a digest. The docstring on `validateConceptProfileWithEvidence` records this.
- `validateConceptProfileWithEvidence` still has no production caller. The enforcement that actually protects stored data is the one inside `storeConceptProfiles`; the validator path is a contract for callers that adopt it, not a gate anything currently passes through.
- No HTTP route reads or writes review decisions, and no profile write route was added. `GET /api/research/concept-profiles/:profileId` is unchanged and profiles stay `INTERNAL`. The new model is added to the API's central non-generic set, so `user`, `superadmin` and `system` all get a refusal for `read`, `create`, `write`, `unlink` and `action` on `knowledge.concept_profile_review_decision` through generic REST and JSON-RPC; `apps/api/tests/record-rules.test.ts` asserts that, and the only access path remains the two service functions.
- Recorded, deliberately not changed here: `knowledge.concept_profile_version` and `knowledge.textual_alignment_candidate_version` are not in that non-generic set, so `canAccess` grants `user` and `superadmin` a generic read of stored profile versions within their active company. That is older than this batch, and moving those two into the set would change existing behavior that other tests depend on, so it stays an open owner decision rather than a drive-by edit.
- The only independence rule implemented is "not the author of the reviewed version, inside the same company". Which role may review a theology profile, whether a review can be withdrawn (it cannot be edited or deleted, only contradicted by a different reviewer), and retention of the rationale text are governance decisions the owner has not made.
- Accepted content still resolves only against the owner-approved samples (Tanzil Q7:46, WEBP Genesis 1:1) and readable canonical evidence. This unit adds no RUH/HIZAB mapping, no source-derived interpretation, and no new source scope.
- The card declares its file scope as `ontology/domains/` and `research/profiles/`, while this unit and its predecessors since `d1670a39` implement in `packages/research/` and `packages/orm-knowledge/`. That discrepancy predates this batch and is recorded rather than quietly retargeted: widening or narrowing a card's declared scope is an owner edit, and the previous evidence rows never claimed the schema directory was touched.

- Read-only API commit: `1013be182de60cc1e581b88a28d889a9d11d7420` adds one exact tenant-scoped profile/version GET route and synthetic authorization tests; it does not change the profile-digest review policy.
- Scope: `ontology/domains/concept-profile.schema.json`, schema-backed validation in `@moonwitness/research`, `@moonwitness/orm-knowledge` persistence/resolver services, and synthetic concept/review fixtures. The approved existing Q7:46 sample is used only to verify local provenance; it receives no lexical gloss or theological mapping here.

## Implemented

- Added a versioned JSON Schema for concept profiles with a stable concept ID, distinct profile ID, tradition, optional community/school and language, interpretive scope, epistemic status, explicit uncertainty, and one or more human interpretations.
- Multiple profiles may describe the same concept while retaining separate tradition/community scopes and different interpretations.
- Each interpretation is explicitly `human_interpretation`, never revelation. Accepted interpretations must name at least one evidence ID; candidate and rejected interpretations remain representable.
- Synthetic tests prove divergent profiles remain separate and reject revelation claim types, missing uncertainty, and accepted interpretations without evidence IDs.
- Added `validateConceptProfile` as the package structural validator and `validateConceptProfileWithEvidence` for evidence prerequisites. It requires a trusted resolver to return matching valid canonical evidence metadata, accepted nonconflicting review consensus, and readable access; missing, mismatched, denied, malformed, or throwing resolver results fail closed. Even when these checks pass, an accepted interpretation returns `profile_review_pending`; K3 Assertion review does not decide a profile digest.
- The async validator snapshots the entire input before awaiting a resolver and rejects any caller mutation detected before completion. Tests cover evidence-ID injection, candidate-to-accepted mutation, and malformed resolver results.
- Added optional `textual_observations` separate from `human_interpretation`. An observation stores only the canonical source/edition/locator/hash, Unicode-scalar range, digest of the selected span, and `unreviewed` state; it does not copy selected text or assert a gloss, translation, doctrine, or concept mapping.
- Added `validateConceptProfileTextualObservations`, which fails closed on missing/malformed/denied or mismatched canonical passages, source hash mismatch, invalid ranges, selected-span digest mismatch, and input mutation during resolver awaits. The trusted resolver must itself read and verify local source bytes and rights metadata; the package contract is not an authorization boundary.
- Added `resolveConceptProfileEvidence` in `@moonwitness/orm-knowledge`. Within one PostgreSQL transaction it rechecks active user/role/company membership, locks and loads the active immutable graph snapshot, binds the evidence record to its exact Assertion and `content_revision`, enforces the INTERNAL visibility ceiling, and verifies the locally pinned passage bytes/hash.
- The resolver derives active-company review consensus from digest-checked, schema-checked review events joined to their workflow instance/event, exact resource record, reviewer/requester canonical identities, reviewer role, action, revision, and idempotency key. One independent accepted decision for the exact Assertion revision is sufficient when company history has no contradictory outcome; a decision for another Assertion revision does not carry forward. A later unrelated graph release does not invalidate an unchanged Assertion revision's decision.
- Owner clarification (2026-10-17): profile-interpretation decisions remain pending until a separate policy and review binding approve the exact profile digest. The K3 independent-review rule applies only to an exact Assertion revision used as source evidence; it does not approve a profile interpretation. Accepted Assertion evidence remains `INTERNAL`; the resolver does not publish it.
- Added an ORM regression that creates an actual accepted K3 decision for the exact synthetic Assertion revision, confirms its evidence resolves as accepted/readable, then verifies an interpretation marked `accepted` is still rejected because no exact profile-digest review binding exists and no profile row is written.
- Added a research-package regression confirming the public evidence validator also keeps an accepted interpretation pending when its resolver returns accepted/readable K3 Assertion evidence.
- Added immutable PostgreSQL-backed concept-profile versions with company/profile/version uniqueness, canonical JSON SHA-256 digests, explicit `INTERNAL` visibility, and database append-only triggers. Same-content retries are idempotent; changed content appends a version; profiles with divergent tradition/scope retain separate IDs.
- `storeConceptProfiles` and `readConceptProfileVersion` use authenticated user/superadmin and active company membership context, lock the authorizing user/company/membership rows through the transaction, scope queries by company, and verify stored digest/schema on reads. No HTTP route or generic CRUD permission is added.
- Added `GET /api/research/concept-profiles/:profileId` with an optional positive version. It returns one exact tenant-scoped `INTERNAL` profile after the store service rechecks current membership, stored digest/schema, readable evidence, and approved local observation bytes. Missing, foreign, revoked, corrupt, or stale profiles receive the same generic 404; the response is `private, no-store`. The endpoint exposes no list or mutation path, and accepted interpretations remain rejected while exact profile-digest review policy is pending.
- K3 review decisions bind Assertion revisions, not profile interpretations. Profile interpretations marked `accepted` fail closed until a decision can bind the exact profile digest. Candidate/rejected evidence IDs must resolve to canonical, readable evidence in the current company; their review consensus may remain unreviewed or conflicting. Duplicate profile IDs in one submitted document are rejected before writes.
- Added a bounded local corpus bridge for textual observations. It admits only the exact approved Tanzil Q7:46 and WEBP Genesis 1:1 source/edition/locator tuples, requests `read_analyze` from the existing offline corpus readers, verifies source identity against the pinned manifest, and passes source bytes/hash to the span validator. Every other source, edition, or locator fails closed before persistence. The corpus witness reader now checks the explicitly requested use against manifest rights while preserving `quote_excerpt` as its default for existing callers.
- Added local store tests for both approved passages, checking persisted records contain only the selector, source hash, scalar offsets and selected-span digest (no source text). Negative tests cover unknown source/edition/locator and mismatched source hash; corpus tests verify `read_analyze` is denied when not present in rights. These are provenance/metadata tests only: they add no source-derived interpretation, mapping, or text copy.
- The corpus root is supplied by the caller; the HTTP read route binds it to the repository's trusted corpus root. This package adapter does not authenticate or pin filesystem paths by itself.
- Added synthetic ORM/workflow tests for accepted and unreviewed evidence states, conflicting outcomes, inactive company membership, Assertion revision changes, immutable/idempotent profile versions, duplicate IDs, unavailable evidence, tenant scoping, and append-only guards. Resolver fixtures reuse only the already approved local Tanzil Q7:46 snapshot to verify source provenance; assertions and review/workflow identities are synthetic.
- No source text or substantive RUH/HIZAB interpretation was added. These fixtures make no cross-source or theological claim.

## Remaining acceptance

- Remaining after the 2026-10-25 binding: a policy for which role may record a profile review and whether a recorded review can ever be withdrawn, and the retention treatment of the stored rationale text. Both are owner calls, not code gaps. The mechanism itself is implemented: `accepted` now requires a re-verified digest-bound decision from someone other than the version author.
- Add source-backed RUH/HIZAB profiles and mappings only when their sources and usage are explicitly authorized; preserve divergent readings and scope.
- Extend observation resolution only after additional exact source/edition/locator scope and rights are approved; current bridge intentionally supports only Q7:46 and WEBP Genesis 1:1.
- A read-only HTTP route now exposes one exact profile version; no profile write route or generic CRUD permission is added. Keep HTTP write work behind a separate need and policy review.
- Keep all profiles interpretive and noncanonical unless separately reviewed under the repository's governance.
