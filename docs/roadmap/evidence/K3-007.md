## Implemented

- Added `findDuplicateCandidates` to `@moonwitness/research`. It compares validated assertions using normalized claim features, polarity, scope, context attribution, lifecycle/review eligibility, epistemic/review state, and readable evidence selectors.
- Every candidate has `status: unresolved` and a rationale. Candidate generation cannot merge, update, or assign a canonical identity. It reports bounded features, not semantic certainty.
- The scorer strictly validates visibility and omits hidden records and evidence linked to unreadable assertions. The API raises generic storage `PUBLIC` to an effective `INTERNAL` floor and admits only effective `INTERNAL` records. It returns opaque record/evidence IDs, rationale and counts; claim text and excerpts are not returned.
- Added authenticated `GET /api/research/duplicate-candidates`. Trusted `system` service callers can use it directly; human `user` and `superadmin` callers require an active company context, active company, and active company membership, rechecked in the same PostgreSQL transaction that reads the shared active `research` release. Responses are `private, no-store`. The release is digest-verified and ontology-validated. It performs no network lookup and accepts no arbitrary graph/corpus input.
- The active `research` release is currently a shared corpus. A human caller's company context authenticates eligibility; it does not partition records in that release. Keep tenant-specific/private records out of the shared release; only the approved synthetic pilot and independently approved shared source material are in scope until release records and queries support company scope.
- Added canonical release ceilings in `@moonwitness/orm-knowledge`: 5,000 rows and 8 MiB combined for the canonical manifest and record JSON. Creation rejects oversized data. Reads check manifest/count first, then aggregate bytes from a SQL subquery capped at 5,001 rows; oversized/stale releases fail closed before content materialization. The route passes a 100-pair scorer limit and caps output at 100 candidates and 500 evidence IDs, marking truncation.
- Tests include scorer and API privacy/determinism cases, authenticated-role enforcement, generic malformed/unavailable responses, output cap behavior, OpenAPI contract, and an isolated PostgreSQL API integration fixture with matching internal assertions plus a restricted assertion. The integration checks exact active release digest, unresolved result, anonymous denial and absence of restricted ID/claim text.
- No legacy repository records, external runtime source, or cross-work textual claim are used. Fixtures are synthetic; the route does not establish a real duplicate or G3 research fact.

## Owner decision taken — a graph release is canon-only, never tenant state — 2026-10-25

The owner delegated the pending data-model calls to this session, and this one is decidable from the storage contract alone, so it is taken rather than left open.

- **Decision.** A research graph release is a company-agnostic canon artifact. Tenant-owned research state may not enter a release, in its manifest or in any record; it lives only in the company-scoped version stores. The tenant-isolation bullet above is therefore closed as a precondition that will never be triggered in the release path, and the isolation guarantee for tenant data is the store it is already written to, not a filter applied when reading a release.
- **Both recorded options were rejected, and the storage model says why.** Option (a), a company column on the release tables populated at write time, collides with `packages/orm-knowledge/src/models.ts:119-127`: `knowledge_research_active_releases` is `unique: [['corpus_key']]`, i.e. the schema states there is exactly one active release per corpus for the whole installation. Making records company-bound therefore _requires_ dropping that constraint and redefining "active" per company, which is a different product object, not a column addition. Option (b), per-company `corpus_key` releases, keeps immutability but publishes the same reviewed scholarship N times with N digests, so every review event's `research_release_digest` binding becomes tenant-specific and the shared canon stops being shared — the thing the K3 release exists to provide.
- **The split is deliberate and already consistent across the package.** Every company-owned store declares `company: fields.belongsTo(Company, { required: true })` — `ConceptProfileVersion` (`models.ts:154`), `TextualAlignmentCandidateVersion` (`:179`), `ResearchSuggestionVersion` (`:199`), `StoryVersion` (`:219`) — while none of the release/review models do: `ResearchGraphRelease` (`:85`), `ResearchGraphRecord` (`:99`), `ResearchActiveRelease` (`:119`), `ResearchReviewEvent` (`:131`), nor `ResearchActorIdentity` (`:257`), which is keyed by user. The ontology reinforces it: `ontology/core/assertion.schema.json:7` is `additionalProperties: false`, so a release record cannot carry a company binding even inside its content.
- **Where the invariant is actually enforced, verified rather than assumed.** `createResearchGraphRelease` (`packages/orm-knowledge/src/research-release.ts:173-270`) does _not_ run ontology validation — it checks lineage, digest replay and byte equality, and inserts. The gates are the two places a canon becomes usable: `activateResearchGraphRelease` calls `validateResearchRelease(snapshot.records)` at `:293` and rejects with `INVALID_EVENT_PAYLOAD`, and `readActiveResearchGraphRelease` re-validates at `:459-462` and returns `null` on failure. So a poison release can be _written_ (deliberately: bytes are content-addressed and must stay auditable) but can never be activated or served. The test below pins exactly that shape, including the case where the pointer row is forced behind the activation guard.
- **Tests added** — `packages/orm-knowledge/tests/research-release.test.ts`, file now **12 tests (was 10)**:
  - "refuses to activate a release whose only defect is a tenant-bound record": a complete, otherwise-valid assertion record with `company_id` and `owner_company_id` added. Activation is rejected with `INVALID_EVENT_PAYLOAD`, the previously active canon is still what the corpus resolves to, `knowledge_research_active_releases` still holds one row, and after forcing that row's `release_id` to the poison release with a direct update, `readActiveResearchGraphRelease` returns `null` rather than serving tenant-bound bytes as canon.
  - "keeps one global active pointer per corpus and no company binding on the release tables": asserts `hasColumn` is false for both `company_id` and `company` on all three release tables — a tripwire that fails loudly if someone adds a company column before doing the activation/uniqueness work this decision requires — and that activating a second release for the same corpus replaces the single pointer instead of adding a per-company one.
- **Non-vacuity.** Relaxing only the top-level `additionalProperties: false` in `ontology/core/assertion.schema.json` flips the first test to a failure because the tenant-bound release then activates successfully: the schema is the load-bearing guard, not the test's own setup. The schema file was restored and `git status --porcelain` reports it clean.
- **Follow-on for K5-005.** That card's open item (2) asked for company-scoped review-history storage and could not name a shape for it. This decision supplies one: `knowledge_research_review_events` has no company column (`models.ts:131-147`), so persona review history must be a new company-scoped version store following the `ConceptProfileVersion` pattern, not a query over releases. That is new implementation work in `@moonwitness/orm-knowledge` outside both cards' file scopes; it is unblocked as a design question and still unbuilt, and no acceptance is claimed for K5-005 here.
- **Scope note.** The change is two tests in `packages/orm-knowledge/tests/`, outside K3-007's declared file scope (`packages/research/`, `apps/api/`), taken under the authority delegated to this session and on the same reasoning K7-006 used for putting a boundary contract where it is observable. No production source file and no `ontology/` file was modified by this decision, and no record was written to any real tenant.
- **Verification.** `packages/orm-knowledge` release suite 12/12; the whole package `pnpm --filter @moonwitness/orm-knowledge test` → 9 files passed, 4 skipped (PostgreSQL-only), **89 passed | 12 skipped**; `node scripts/roadmap/validate-roadmap.mjs` → 213 tasks valid; Prettier and `eslint --max-warnings=0` clean on the changed test file. The four PostgreSQL-only suites were not re-run: this decision adds tests only, touches no production code, and the skipped files are PostgreSQL-specific suites this change does not modify.
