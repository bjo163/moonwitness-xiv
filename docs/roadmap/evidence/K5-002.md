- The operational witness read path now checks its canonical subject revocation marker. Other derivative stores and publication surfaces listed above remain outside this slice.
- Blocker for the derivative-store half of this acceptance, recorded 2026-10-25: the story version, suggestion version, concept profile and graph release tables carry no subject reference, so a revocation keyed by `subject_ref_sha256` cannot locate them. Extending invalidation there needs an owner decision about the data model before code: either add a tenant-scoped subject link column populated at write time — which changes every writer signature in `packages/orm-knowledge/` and softens the append-only guarantee other cards protect — or keep those stores subject-blind and treat revocation as a rebuild of derived projections only, leaving revoked content inside the immutable version rows. Neither option was chosen unilaterally. _(Decided on 2026-10-25 under delegated owner authority: subject-blind stores kept — see the data-model decision section below. The two legal/safeguarding questions that decision names are still open.)_
- Extend negative coverage to public/search/preview/export/log/prompt exposure paths with synthetic canaries and zero plaintext exposure. Query/fragment values and malformed URL userinfo are excluded from request logs centrally; the actual privacy revocation/projection routes and failed authentication routes now have synthetic log canary tests. Broader route-level public/search/preview/export/prompt exposure checks and other sensitive logger payload paths remain open. ## Data-model decision taken — subject-blind derivative stores kept — owner authority delegated in-session — 2026-10-25

The blocker bullet above left two options open and said neither was chosen unilaterally. The owner delegated the call to this session, so it is now taken: **keep the derivative stores subject-blind.** Revocation stays a rebuild-and-conceal operation over the surfaces that already carry a subject handle, and physical erasure of immutable version rows is declared an out-of-band operator action, not an application feature. This is a decision, not new code: nothing in `packages/` or `apps/` changed for it.

Reasons, each checked against the current code rather than argued in the abstract:

- **No write-time subject handle exists to populate a column from.** Every version writer takes an opaque, schema-locked document plus the authenticated actor: `storeStoryVersion` (`packages/orm-knowledge/src/story-version-store.ts:275-281`) validates `input.story` against `ontology/domains/story-version.schema.json`, whose `additionalProperties: false` at `:7`, `:25` and `:36` means a story document provably cannot name a subject today. The concept-profile, suggestion and alignment writers have the same shape. Option (a) is therefore not "add a column"; it is "invent a new trusted input every caller must supply".
- **A caller-asserted link would be fail-open.** Nothing in the stored bytes binds a story, profile or suggestion version to a person, so the only way to fill a subject column is to let the writing caller declare it. Omitting the declaration is silent and uncheckable, which would make revocation coverage depend on writer honesty — strictly worse for a privacy control than an explicitly uncovered surface, because the card would then _look_ like it invalidates derivatives while the guarantee is per-caller.
- **A new persistent handle on rows that can never be amended is a permanent privacy liability.** The append-only guards (`installAppendOnlyGuards`, `packages/orm-knowledge/src/manifest.ts:28-98`) are `UPDATE`/`DELETE`-only, so adding an insert-time column is technically legal — that is precisely why a wrong choice there cannot be walked back. Today the only subject handle any table stores is a keyed hash, `syntheticWitnessSubjectRefSha256` = `sha256("moonwitness:knowledge:witness:v1:" + companyId + ":" + externalKey)` (`privacy-revocation.ts:56-61`), never the raw witness key. Spreading that handle — let alone an unhashed one — across every immutable version row would widen exactly the exposure the card exists to reduce.
- **It cannot be backfilled.** Rows written before the migration carry no subject information, so the promise would hold only for later records while the schema suggests otherwise.

What the card now claims, and what it does not:

- Claimed, and already tested: a revoked subject's active projections stop being readable (`readActivePrivacyProjections` `whereNotExists`, `packages/orm-knowledge/src/privacy-revocation.ts:260-271`), owned synthetic-witness access fails closed with `NOT_FOUND` (`packages/orm-knowledge/src/witness-access.ts:225-243`), a reactivated or reinserted projection stays hidden after withdrawal (`apps/api/tests/research-privacy.routes.test.ts:283`), and the revocation row itself is append-only (`manifest.ts:42`, guarded by `installAppendOnlyGuards` at `:28`).
- Not claimed: reach into story, concept-profile, suggestion, alignment or graph-release rows that quote a revoked subject, and physical deletion of any immutable version row. Retention is modeled but not wired: `decidePrivacyRetention` (`packages/research/src/privacy-lifecycle.ts:138-143`) is a pure decision over a caller-supplied `PrivacyRetentionPolicy` and denies access outright when no policy is given, and nothing in this repository stores or supplies that policy — so there is no default retention clock to honor.
- Two decisions still belong to the owner and are not mine to take even under the delegation, because they are legal and safeguarding judgments rather than engineering ones: whether concealment-plus-non-derivation satisfies the erasure right applicable to real witness data, and what the retention durations are. Until both are answered, K5-002 stays `in_progress` and must not be enabled for non-synthetic subject data.
- What would legitimately reopen option (a): a K5-004 authoring flow in which the subject link is attached through the K3-005 authenticated review workflow — reviewed, not caller-asserted — together with a storage shape for company scoping from K3-007. Then the column carries a verified claim instead of a hope.
