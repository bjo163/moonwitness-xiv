## The eleventh addon carries the same menu-without-view defect this card once fixed for `base.audit_log` — `dev` `apps/api/src/whatsapp/manifest.ts` — 2026-10-24

- Found while measuring the cost of promoting the app-local WhatsApp addon, not while running the suite: [apps/api/src/whatsapp/manifest.ts:107-113](../../../apps/api/src/whatsapp/manifest.ts) builds `menus` by mapping over all **five** models, while `views` (`:42-106`) declared only **four** — `WhatsappAccount`, `WhatsappConversation`, `WhatsappMessage`, `WhatsappJob`. So `whatsapp.event` was published as a Development Mode menu with no view behind it.
- This is precisely the defect class recorded as delivered behavior further down this card for `base.audit_log` ("the conformance suite exposed … a Development Mode menu without a declared view"), and the reason it stayed hidden here is structural: `scripts/roadmap/addon-conformance.test.mjs:73-79` asserts menu/view consistency for the ten **package** addons it enumerates at `:23-34`, and `orm-whatsapp` is not in that list because it is not a package. The guard is correct; this addon has simply never been inside its reach. That is also why the per-addon `[x]` claim of this card cannot be extended to WhatsApp until the addon is promoted — item 11 of the owner checklist.
- Fixed by declaring the missing view rather than by dropping the menu, matching the `base.audit_log` precedent: `defineView(WhatsappEvent, …)` with `account`, `external_id`, `status`, `attempts`, `available_at` as list columns, a form section exposing `company`, `account`, `external_id`, `status`, `attempts`, `available_at`, `last_error`, and `external_id` as the search field. `payload` is deliberately left out of both list and form — [apps/api/src/whatsapp/models.ts:89](../../../apps/api/src/whatsapp/models.ts) marks it `hidden: true, sensitive: true`, and the field metadata is what the ORM exposes to generic view screens.
- Validation, with the guard proven live rather than assumed: `pnpm --filter @moonwitness/api exec vitest run tests/whatsapp.routes.test.ts` **13/13 pass**, `pnpm --filter @moonwitness/api build` (tsc) exit 0, `node --test scripts/roadmap/addon-conformance.test.mjs` **2/2 pass**, `prettier --check` clean on the changed file. A mutation probe renaming the search field to `external_id_MUTATION_PROBE` fails the suite at import time with `Error: Unknown field in view for whatsapp.event: external_id_MUTATION_PROBE`, which proves both that the new view is executed by existing tests and that field names are validated rather than ignored ([packages/orm/src/view.ts:199-207](../../../packages/orm/src/view.ts)). The file was restored from the pre-mutation string, and `git diff --stat` after restore shows the additive 21 lines only.
- The promotion cost itself is now enumerated rather than estimated, and it corrects my own earlier wording in [M9.08 evidence](M9.08.md) ("five coordinated call sites"): a full survey of the generator, build and guard surface finds **sixteen** hardcoded sites across six files, with two of them load-bearing in opposite directions. `pnpm -r build` discovers a new package automatically (`pnpm-workspace.yaml:1-3`, used by `ci.yml:93`, `ci.yml:208` and `Dockerfile:39`), so CI quality, CI integration and the image build need no edit. What must be edited: the addon entry arrays in `scripts/docs/generate-reference.mjs:259-291`, `:292-303` and the env-source list at `:384-394`; `scripts/architecture/generate-diagrams.mjs:11-64`; the four root `&&`-chains in `package.json:56`, `:63`, `:74`, `:75`; the fifteen explicit per-package build steps in `.github/workflows/pages.yml:241-269`; `test:unit:built` in `package.json:136`; `scripts/run-unit-tests.mjs:105-177`; `scripts/roadmap/addon-conformance.test.mjs:7-17`, `:23-34`; `scripts/check-coverage.mjs:36-47` with `docs/testing/coverage-thresholds.json`; `scripts/run-postgres-tests.mjs:34-64`; and a `COPY packages/orm-whatsapp/package.json` line in `Dockerfile:10-35`, which `scripts/docker-workspace-manifests.test.mjs:19-35` enforces by scanning the filesystem against the Dockerfile.
- Two constraints the survey surfaced that are easy to get wrong, recorded before anyone attempts the move. (1) Routes must stay where they are: the API reference scrapes `apps/api/src/routes` specifically (`generate-reference.mjs:401`), and the nineteen `/whatsapp/*` and `/internal/whatsapp/*` rows already present in `generated-api.md` would silently disappear if the route file moved into the package. (2) Package version and addon identity are different numbers and both are pinned: `scripts/check-release.mjs:47-61` collects mismatches from every workspace manifest it discovers at `:26-33` and fails the release check if any `@moonwitness/*` package version differs from the root `1.0.0-rc.1`, while the manifest's own `version: '1.1.0'` (`apps/api/src/whatsapp/manifest.ts:21`) is the identity stored in `_orm_addons` by `installAddons` (`packages/orm/src/addon.ts:411-414`) and must not be bumped as part of a directory move.
- Not attempted in this turn, on purpose: the promotion itself. It edits six files of gate wiring while three other workers are landing commits on the same branch every few minutes, and `scripts/promotion-risk.mjs:3-12` classifies exactly this shape (`packages/orm-whatsapp/package.json`, `.../src/models.ts`, deleting `apps/api/src/whatsapp/*`) as promotion-sensitive. The measured inventory above is the input the owner needs to decide whether to promote or to keep the addon app-local and accept that its five models stay out of the generated reference; the defect that would have broken the first conformance run for it is already fixed here.
