## Candidate review decision surface — 2026-10-25

- Status: the review/decision surface named by the earlier sections is implemented at service level in `packages/research/` and `packages/orm-knowledge/`. No HTTP route was added, so candidate review is not yet reachable by a caller; that gap is deliberate and is recorded below.
- Product rule taken as the decision boundary: an accepted outcome says a human admits this model output for the tenant's own follow-up work. It is a verdict about a candidate only — the stored suggestion stays `INTERNAL` and `unreviewed`, and accepting it writes no canonical record. `packages/research/src/research-suggestion-review.ts` carries that rule in its docstring, and the shape has no field that could carry a promotion: `Object.keys()` of a minted decision is exactly `company_id, decided_at, id, kind, outcome, rationale, reviewed_version, reviewer_id, suggestion_digest, suggestion_id`, and a test asserts that set.
- Mint boundary: `mintResearchSuggestionReviewDecision` is the only producer of an authorizing decision and it binds the decision to the minting `(company_id, reviewer_id)` pair inside a module-private `WeakMap`, so a spread clone or a `JSON.parse(JSON.stringify())` copy reads as a valid decision and authorizes nothing. `authorizesResearchSuggestion` requires attestation for the tenant plus `outcome === 'accepted'` plus identity and digest equality. This is the third instance of the pattern (`concept-profile-review.ts`, `textual-alignment-candidate-review.ts`, now this) and each instance is its own brand — a K4-005 candidate decision cannot authorize a suggestion read.
- Storage boundary: `recordResearchSuggestionReviewDecision` runs inside a transaction after active user/company/membership checks and the company-row `forUpdate` lock, reads the newest (or pinned) stored version of the tenant, refuses the actor who stored that version, re-hashes `suggestion_json` against `suggestion_digest`, then inserts, re-reads and mints. Replaying the same reviewer + digest + version + outcome returns the existing decision; a different outcome or version for that pair throws. `resolveResearchSuggestionReviewDecision` re-runs the full re-verification on read, so an out-of-band privileged edit of the reviewed bytes yields `Research suggestion review decision failed its own integrity check` rather than an authorizing object. The table `knowledge_research_suggestion_review_decisions` is append-only in both PostgreSQL and SQLite; `unique (company, suggestion_digest, reviewer)` makes one reviewer's verdict per canonical digest exactly one row.
- Digest equality is enforced here and not in the pure validator, because the two packages canonicalize differently (`canonicalResearchJson` for persisted digests vs `stableJson` for the profile validator). The store/mint boundary is therefore the only place the two can be reconciled, and that is where the check lives.
- Deliberate boundary the reviewer must know: recording and resolving a review re-verify the stored bytes, their canonical form, the envelope schema, the embedded id and the `INTERNAL`/`unreviewed` ceiling. They do not re-run the citation resolver against current source, Assertion and Evidence access. The single-candidate read route still does, so a reviewer who opens the candidate before deciding sees live source validation; a decision row alone is not a statement that the citation is still live today.
- Exposure: `knowledge.research_suggestion_review_decision` joins `NON_GENERIC_MODELS` in `apps/api/src/auth/policy.ts`, so generic REST and JSON-RPC deny it for `user`, `superadmin` and `system` alike regardless of any grant. Unlike the version tables, the three review-decision tables are not also seeded into the `base.model_access` default-deny array — the central deny already applies to every role and the K4-004/K4-005 precedent kept them out; recorded rather than changed.
- Scope note: the card's File scope is `packages/local-ai/`, `apps/api/`, but this work landed in `packages/research/` and `packages/orm-knowledge/`. Nothing in `packages/local-ai/` changed: the review is about a stored candidate, not about how one was generated, and `apps/api/` was touched only to extend the generic-API deny list. The scope discrepancy is recorded here rather than silently retargeting the card.

## Implemented

- Added a closed JSON Schema envelope with a version marker, at most 20 suggestions, and exactly three kinds: summary, term, and duplicate. Unknown properties are rejected.
- Every candidate is constrained to `unreviewed` and `INTERNAL`, with canonical suggestion, Assertion, and Evidence identifiers and bounded citation metadata.
- Citations bind exact source/edition/locator, full-source SHA-256, Unicode-scalar range, and selected-span SHA-256. The trusted resolver rechecks source identity, digest, readability, and selected-span digest.
- Summary text must exactly equal its cited spans in order; term text must exactly equal its one cited span. Duplicate suggestions require two distinct active/readable Assertions and readable active Evidence bound to each requested Assertion. The schema includes no rationale or merge instruction fields.
- `validateResearchSuggestionEnvelopeWithResolver` fails closed on malformed envelopes, unavailable or mismatched sources, invalid spans, unsupported text, unreadable/inactive records, and invalid Evidence-to-Assertion bindings for every suggestion kind. Each citation must resolve an active/readable Assertion and active/readable Evidence bound to that Assertion. It performs validation only and has no canonical write path.
- The async validator snapshots JSON input before resolver awaits, gives the resolver detached selectors, and returns only the validated snapshot. The ORM store persists that return value rather than rereading caller-mutable input.
- Store and read services snapshot authenticated user, company, role, identifier, and requested version fields before asynchronous work. Store authorization and transaction-scoped resolver validation run in the write transaction after active user/company/membership checks and the company lock.
- The store requires a `resolverForTransaction(trx)` factory; there is no resolver-only persistence path. Trusted callers bind authoritative source, Assertion, Evidence, and access checks to the same transaction as candidate insertion.
- Added immutable PostgreSQL suggestion versions scoped by active user, company, and membership. Each complete suggestion is stored as hidden canonical JSON with its digest, version, `INTERNAL` visibility, and `unreviewed` state. Exact retries are idempotent; changed content appends a new version; company-row locking serializes version allocation.
- Reads remain company-scoped, verify active membership, the stored digest, canonical JSON shape, and `INTERNAL`/`unreviewed` status, then revalidate each citation's current passage bytes, Assertion state/readability, and Evidence state/readability/binding through a resolver bound to the same transaction. Failure returns no suggestion. Append-only triggers reject SQL `UPDATE` and `DELETE`. The store has no path to canonical graph writes.
- Added `POST /api/research/suggestions/generate`. It accepts only a suggestion kind and one or two evidence IDs, requires authenticated active-company membership, and resolves exact local Tanzil Q7:46 or WEBP Genesis 1:1 snapshots. It does not accept company IDs, source text, Assertion IDs, or runtime settings from the caller.
- Added `GET /api/research/suggestions/:suggestionId` with an optional positive version. It requires an authenticated active-company `user`/`superadmin`, queries only that tenant's exact candidate, and returns its complete validated suggestion only as `INTERNAL`/`unreviewed` with `private, no-store`. A pre-read only constrains resolver inputs; the immutable store row is reloaded and its digest, canonical shape, exact local source bytes, current Assertion/Evidence readability and bindings are revalidated inside the store transaction. Missing, foreign-tenant, revoked, corrupt, and stale-source candidates produce the same generic 404. It has no list, review, mutation, or publication operation.
- The route validates provider output against resolver-backed active tenant evidence and rechecks exact local source bytes. Persistence uses the transaction-aware resolver hook so the current actor, active research release, source authorization, and evidence bindings are checked again inside the same transaction that appends the candidate. The response contains only candidate IDs/version/digest and is `private, no-store`.
- Route tests use synthetic active research records and a deterministic fake runtime; they cover both approved samples, unauthenticated and malformed requests, unavailable and cross-company evidence, source substitution, and membership revocation during provider generation. Read-route coverage verifies authenticated retrieval of the exact candidate, `private, no-store`, generic cross-company denial, unauthenticated denial, and malformed version rejection. Valid candidates are stored and read only as `INTERNAL`/`unreviewed`.
- Tests byte-check the two approved local sample artifacts and exercise malformed shapes, citation/span mismatch, unsupported text, duplicate binding, resolver-await caller mutation, evidence/access revocation before transactional revalidation, tenant access, idempotency, append-only rules, and tamper detection.
