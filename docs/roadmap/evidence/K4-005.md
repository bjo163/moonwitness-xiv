## Candidate-digest review binding — 2026-10-25

The card asked for _reviewed_ textual parallel candidates, and the previous batch stored only unreviewed versions. This unit adds the review decision itself; it mirrors the K4-004 profile-digest binding for a different subject.

- Product rule decided for this unit: an accepted outcome says a reviewer admits this pairing as a parallel worth carrying in this tenant. It cannot widen what the candidate claims — the interpretation boundary is part of the reviewed bytes, so a candidate that asserted identity, quotation, fulfilment or doctrine would carry a different digest and no decision of this kind would describe it. This is why the card's `parity/similarity never implies identity or fulfilment` acceptance line needs no extra flag on the decision record.
- `packages/research/src/textual-alignment-candidate-review.ts` defines the decision and its unforgeable brand, following `attestedResolutions` in `packages/research/src/evidence.ts` and the K4-004 `decisionAuthorities` WeakMap. `mintTextualAlignmentCandidateReviewDecision` registers the returned object with its reviewing company and reviewer in a module-private WeakMap, so a spread clone or a JSON round-trip is structurally identical and unauthorized; the object is frozen. Minting refuses a blank or over-long id, a candidate id outside `mw:textual-alignment-candidate:…`, a digest outside 64 lowercase hex, a reviewed version below 1 or not a safe integer, an outcome outside `accepted`/`rejected`, an unparseable `decided_at`, and a blank or over-4000-character rationale.
- Unlike the profile decision, this record carries no `reviewed_digest`: the reviewed subject is the stored candidate version itself, identified by `candidate_id` plus `candidate_digest`. `authorizesTextualAlignmentCandidate(decision, companyId, { candidate_id, candidate_digest })` requires minted-in-this-company, `outcome === 'accepted'`, and both identity and digest matching the subject.
- New append-only table `knowledge_textual_alignment_candidate_review_decisions` (model `knowledge.textual_alignment_candidate_review_decision`, addon manifest `1.7.0` → `1.8.0`), unique on `(company, candidate_digest, reviewer)`, with the candidate identity and digest, reviewed version, outcome, reviewer, `decided_at`, and a hidden rationale. Both append-only branches are asserted: the SQLite `RAISE(ABORT, 'Textual alignment candidate review decisions are append-only')` chain and the PostgreSQL trigger function.
- `recordTextualAlignmentCandidateReviewDecision(db, …)` runs in one transaction: recheck the authenticated actor's active company membership, lock the company row, read the newest (or a caller-pinned) stored candidate version for that company, refuse its submitter as reviewer, re-hash the stored bytes against `candidate_digest`, then insert. A repeat of the same reviewer and same candidate digest is idempotent and returns the same decision; the same pair with a different outcome or a different reviewed version fails, so a reviewer cannot overwrite their own verdict.
- `resolveTextualAlignmentCandidateReviewDecision(db, …)` returns the newest accepted decision for one exact candidate identity and digest inside the reader's active company. Every read re-enters the mint path against storage, so it returns null rather than an authorizing object when the reviewed version has gone missing, its bytes no longer match the bound digest, the reviewer turns out to be the submitter, or the stored row no longer satisfies the citation-only projection. Recording a decision on a version row that breaks that projection fails inside the transaction and writes nothing.

### Boundary this unit does not cross

- No consumer yet: nothing in the graph release, suggestion, or story paths reads `authorizesTextualAlignmentCandidate`, and `storeTextualAlignmentCandidates` still accepts unreviewed candidates — that is their correct state. An "accepted alignment" projection artifact is a separate deliverable, not a flag on the candidate.
- Digest equality is enforced at the store/mint boundary. `packages/research/src/textual-alignment.ts` projects with `stableJson` while `packages/orm-knowledge/src/research-release.ts` persists with `canonicalResearchJson`; the two are deliberately not interchangeable, so only the store can bind bytes to a digest. Same split as recorded for K4-004.
- No HTTP route reads or writes candidate reviews, and no candidate write route exists. The new model is added to `NON_GENERIC_MODELS` in `apps/api/src/auth/policy.ts`, so `user`, `superadmin` and `system` are refused for `read`, `create`, `write`, `unlink` and `action` on `knowledge.textual_alignment_candidate_review_decision` through generic REST and JSON-RPC; `apps/api/tests/record-rules.test.ts` asserts it. Recorded, deliberately not changed here: `knowledge.textual_alignment_candidate_version` is still not in that set, which predates this batch.
- The only independence rule is "not the submitter of the reviewed version, inside the same company". Which role may review a cross-tradition pairing, whether a recorded review can be withdrawn (it cannot be edited or deleted, only contradicted by a different reviewer), and retention of the rationale text remain owner governance calls.
- Sources stay inside the owner-approved sample limit (Tanzil Q7:46, WEBP Genesis 1:1) and synthetic fixtures. This unit records no parallel between the approved samples, imports no legacy repository, and adds no four-tradition witness data; the fixtures name synthetic passages only.
- The card declares its file scope as `packages/research/` and `research/profiles/`; this unit touches `packages/research/` and `packages/orm-knowledge/`. `research/profiles/` does not exist in the repository and the candidate store has lived in `packages/orm-knowledge/` since `c50057e2`. The discrepancy predates this batch and is recorded rather than quietly retargeted — widening a card's declared scope is an owner edit.

## Implemented

- Added a strict public input contract for a candidate that names two distinct canonical evidence IDs and exact source, expression, edition, locator, content hash, Unicode-scalar range, and quote selectors.
- Resolve each side independently through a caller-provided trusted resolver. The resolver must be bound to the authenticated active tenant and verify canonical evidence, local source rights, edition, locator, and tradition metadata. Resolver-provided tradition context is used; the candidate cannot label its own tradition context.
- Verify canonical passage digest and exact quote/range correspondence before projection. Reject malformed identifiers, extra fields, invalid digests, invalid/out-of-bounds ranges, quote mismatch, malformed Unicode, and identical selectors.
- Snapshot public input and pass detached, frozen selectors to asynchronous resolution so mutation during awaits cannot change the validated identity or citation.
- Project citation-only records with no full passage text. Output is always `TextualParallelCandidate` with `candidate` status and explicit false assertions for identity, quotation, fulfillment, and doctrine.
- Similarity score and method/version are validated caller-supplied metadata. This function does not compute similarity and makes no source-parallel, theological, or historical conclusion.
- Added `TextualAlignmentCandidateVersion` and `storeTextualAlignmentCandidates`/`readTextualAlignmentCandidateVersion` to ORM Knowledge. The store locks and verifies active user, company, and membership in the transaction, re-projects each untrusted input through the supplied trusted passage resolver, hashes canonical citation-only JSON, scopes versions by company, retries identical digests idempotently, and appends changed versions.
- Candidate rows are restricted to `INTERNAL`, denied to the ordinary generic read group, and protected by ORM hooks and SQLite/PostgreSQL append-only triggers. Reads verify tenant access, canonical digest, exact projected object shape, quote range metadata, and interpretation-boundary flags; full passage text and unexpected nested fields are rejected.
- PostgreSQL integration covers concurrent same-digest writes, append-on-change, read scoping, INTERNAL visibility, and append-only deletion. Fixtures use synthetic passages only.
- Tests use synthetic witness passages only. The approved local Tanzil Q7:46 and WEBP Genesis 1:1 samples are not represented as cross-source parallels or used as fixtures in this task.
- No legacy repository is connected or imported, no runtime fetch is introduced, and no screenshot PNG is modified.

This approval does not establish a parallel between those samples, approve private witness/account/child data, or authorize general publication.
- The owner approved the K3 rule for a later exact Assertion revision review: one independent reviewer may approve when active-company history contains no contradictory decision. Candidate storage still accepts unreviewed versions — that is their correct state — and from 2026-10-25 an independent reviewer can additionally record an accepted or rejected verdict bound to one exact stored candidate version and digest.
- Before activating private data, retention and access revocation must be defined. Actual four-tradition witnesses and rights/usage approval for each source are still required. The product-level review subject rule this file previously listed as missing is now decided and implemented: a cross-witness candidate is reviewed as itself (candidate identity + canonical digest of the stored version), not as an Assertion revision, so the generic K3 exact-Assertion rule and this candidate rule stay separate subjects and neither substitutes for the other.
