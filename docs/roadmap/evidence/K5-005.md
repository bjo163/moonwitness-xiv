## Scope check on the accepted-decision gate — 2026-10-25

This unit changed no code. It re-reads the gate the card's acceptance line depends on, because that line — "no equation of narrative persona with historical/theological person without review" — is only as strong as what the validator can actually tell about a decision.

- What the gate does check (`packages/research/src/persona-canon.ts:89-135`): an association needs exactly one decision plus its candidate; the decision must itself pass `validateIdentityDecision`; its `outcome` must be `'accepted'`; `decision.id` must equal the association's `decision_id`; `decision.candidate_id` must equal the candidate's id; both the persona and the associated identity must be one of the candidate's two endpoints and not each other; and the decision's preserved conflict set must equal the candidate's conflict set exactly.
- What it cannot check: `acceptedDecision` and `candidate` are parameters the caller supplies (`persona-canon.ts:46-50`), and `recordIdentityDecision` (`packages/research/src/identity-reconciliation.ts:128-161`) is a pure constructor that copies `outcome`, `reviewer_id`, `reviewed_at` and `evidence_refs` straight out of its `input` argument (`:148-157`). It never compares `reviewer_id` to an authenticated actor, never consults a workflow instance, and never requires the reviewer to differ from the persona's author. So a caller can obtain a structurally perfect "accepted" decision for any candidate by asking for one, and `persona-canon.ts:114` will read the conflation authorization the acceptance line reserves for a review.
- Consequence for review. This is the self-certification path K3-005's acceptance forbids for research review events, still open on the identity-decision surface: K3-005 governs `ResearchReviewEvent` through a locked workflow transaction, but the persona validator consumes a standalone decision object, not that workflow. The card cannot be accepted as review-authorizing until an accepted identity decision is produced only by an authenticated, non-self-certifying reviewer path.
- Why the fix is not this card's scope. `K5-005` declares `corpus/reference/` and `ontology/mappings/`. The two candidate fixes live elsewhere: (a) a brand on reviewer-accepted decisions — the equivalent of what K4-003 landed for evidence on 2026-10-25, where `resolveResearchEvidenceReference` registers each minted object in a module-private `WeakSet` and `isAttestedEvidenceResolution` refuses anything a caller hand-built — belongs to the K3-003 contract in `packages/research/src/identity-reconciliation.ts`, which `relation.ts:323` also consumes, so it is a cross-card contract change; (b) resolving the decision from trusted, company-scoped storage belongs to `@moonwitness/orm-knowledge` and the review API, and is blocked by the same unresolved owner decision recorded under K3-007 on 2026-10-25: a graph release is keyed by `corpus_key` alone and its records carry only `key/kind/visibility/content`, so there is no company column to scope a persona's review history against without either populating one at write time or issuing per-company releases.
- Owner decision needed, in this order: (1) confirm that a `mw:persona:*` → `mw:entity|agent:*` association may be authorized only by an authenticated reviewer through the K3-005 workflow, which makes the brand/attestation change a K3-003 work item _(decided yes and implemented on 2026-10-25 — see the section below; the K3-005 workflow binding itself is still open)_; (2) settle the K3-007 company-scoping question, because until it is settled a company-scoped review-history read for personas has no storage shape to target; (3) name the source scope for real alias/role mappings — `source_refs` currently checks internal attribution only (`K5-005` Status above), and the only approved sources remain Tanzil Q7:46 and WEBP Genesis 1:1, which carry no persona corpus.
- What is already correct and needs no owner action: namespace separation (`mw:persona:*` never collapses into `mw:entity|agent:*` by default), alias/role source attribution against `source_refs`, rejection of `same_as` and canonicalization properties, and the synthetic-only fixture posture. No record was written and no association was authorized by this check.

## Accepted-decision brand implemented — owner decision taken in-session — `kseries-local` — 2026-10-25

The owner delegated the pending calls to this session ("take over"), so item (1) of the owner-decision list above is decided and implemented rather than left open. Item (2) (K3-007 company-scoped storage) and item (3) (real alias/role source scope) stay undecided and are **not** claimed as closed here.

- Decided contract: an accepted identity decision is only as authorizing as the object that was minted with it. `recordIdentityDecision` (`packages/research/src/identity-reconciliation.ts:153`) now takes a third argument `{ company_id, reviewer_id }`, refuses an empty company or reviewer, refuses a `reviewer_id` that differs from the decision's own (`:174-179`), and records the pair against the returned object in a module-private `WeakMap`. `isAttestedIdentityDecision(decision, authority)` (`:141`) is true only for that object under that exact company **and** reviewer. This is the same unforgeable-brand pattern K4-003 already uses for evidence (`evidence.ts:83`, `:89`), extended with the two bindings this contract actually needs because a decision names a reviewer and belongs to a tenant.
- Gate that consumes it: `validateNarrativePersona` (`packages/research/src/persona-canon.ts:114-125`) refuses any association whose decision was not minted for the supplied authority, with the new `attested_decision` issue, before the structural comparison runs. A caller that cannot name a reviewing context gets no association even when it holds the genuine object.
- What this closes: a hand-built literal, a field-for-field clone, and a JSON round-trip of a real decision can no longer authorize conflating `mw:persona:*` with `mw:entity|agent:*`. Before this change all three did, because `persona-canon.ts` read only `outcome === 'accepted'` off a caller-supplied object.
- What this does **not** close, stated plainly so the card is not over-accepted: (i) trust still sits with whoever calls `recordIdentityDecision`, exactly as it does for the evidence `lookup` callback — the brand proves a mint happened, not that a human did it, so binding the mint to the K3-005 authenticated workflow is still open; (ii) `validateResearchGraph` → `validateIdentityRelation` (`packages/research/src/relation.ts:320`) still validates serialized decisions from a graph document and deliberately does **not** require attestation, because a release document can only ever contain serialized copies — that path needs the digest-bound review-event read K3-005 owns; (iii) company-scoped review-history _storage_ is still undefined pending K3-007.
- Scope note. The change lives in `packages/research/`, which is `K3-003`'s declared file scope and is not in `K5-005`'s (`corpus/reference/`, `ontology/mappings/`). K3-003 is otherwise closed, so this is a contract hardening on a finished card taken under the delegated owner authority; `relation.ts` was touched only in its test. Nothing outside `packages/research` referenced `recordIdentityDecision` or `validateNarrativePersona` (repo-wide grep returns zero callers in `apps/`, `ontology/`, `corpus/` or `scripts/`), so no production path changed behaviour and none can break.
- Tests: `packages/research/tests/identity-reconciliation.test.ts` adds binding checks (minted object attested; clone, `JSON.parse(JSON.stringify())`, foreign company and foreign reviewer all refused; reviewer-spoofing and blank-company mints throw) and `packages/research/tests/persona-canon.test.ts` adds a refusal test for the three forged forms, re-targets the stale-conflict case so it still reaches the conflict comparison through a genuinely attested decision, and pins that minting against a conflicted candidate cannot drop a conflict. `pnpm --filter @moonwitness/research test` → **15 files, 103 passed** (was 101); `build` clean; Prettier clean; ESLint `--max-warnings=0` clean on all five files.
- Repository defect found while verifying this: `packages/research/tsconfig.test.json` extends `./tsconfig.json`, which sets `exclude: ["node_modules", "dist", "tests"]`, and the child overrides only `include`. So `tsc -p tsconfig.test.json` typechecks `src` alone and exits 0 even when a test file calls a function with the wrong arity — the arity error in `relation.test.ts:262` surfaced only when vitest executed it. Fixing that inheritance (drop the stale `exclude`, or set `exclude: ["node_modules", "dist"]` in the child) would typecheck every package's tests and may expose pre-existing test-side type errors, so it is a repo-wide change belonging to the owner's CI decision, not to this card.
