## Implemented

- `ontology/core/research-review-event.schema.json` defines the versioned `ResearchReviewEvent` contract. Events bind the assertion/relation revision, active graph release digest, workflow instance/event sequence/revision, outcome, reviewer/requester, exact evidence IDs, visibility, idempotency key, and timestamp.
- `@moonwitness/orm-workflow` accepts an optional transaction-scoped payload preparation callback after locking the workflow and validating its transition. The prepared payload and workflow state/event are committed together. Exact idempotent replays compare the stable request intent and do not rerun the callback. Callback or event insertion failure rolls back the transition.
- `@moonwitness/orm-knowledge` stores immutable canonical PostgreSQL graph release manifests and records, an expected-head active-release pointer, append-only review event rows, and explicit append-only mappings from database users to canonical `mw:user:*` IDs. No SQL user ID is converted into an ontology identity automatically. Active-release reads also fail closed if a corrupted pointer resolves to a valid release for a different corpus.
- `transitionResearchReview` validates inside the locked workflow transaction that the workflow resource is a record in the active verified release and that the requested subject, revision, and evidence association match that release. It validates the full graph, verifies evidence selectors against pinned local corpus bytes, derives requester identity from the workflow starter, checks authenticated user role/company membership, and persists the event atomically with the workflow transition.
- Explicit reviewer/requester identity mappings are provisioned only by `POST /api/research/actor-identities`, restricted to an authenticated superadmin. The caller cannot choose the provisioner or request ID; the route derives those from the authenticated session and request context. Mapping insertion and its append-only `base.audit_log` event share one PostgreSQL transaction; mappings are never updated/deleted, and conflicting or mismatched replays fail closed.
- Evidence visibility is floored at `INTERNAL` when generic storage says `PUBLIC`; a public storage flag cannot confer publication approval. Event visibility is at least as restrictive as the subject and all selected evidence.
- Only terminal approved/rejected transitions create a research decision projection. Intermediate workflow votes remain in the append-only workflow event log. `POST /api/research/reviews` starts a subject-bound review, `POST /api/research/reviews/:id/decision` records an approved/rejected decision through the transactional adapter, and `GET /api/research/reviews/:subjectId/history` returns a bounded, integrity-checked, company-scoped history with a stable cursor. The generic workflow APIs hide research reviews and reject generic starts/actions, so decisions cannot bypass source/evidence validation.
- The dedicated API accepts only authenticated `user` or `superadmin` reviewers. Decisions recheck active company membership and company status in the locked transaction. Subject and evidence visibility above `INTERNAL` are denied; history responses are `private, no-store`. Stored event digest/schema and all indexed binding columns (workflow ID/sequence, subject/revision, release digest, idempotency key) must match before history is returned or a later decision proceeds.
- SQLite tests cover assertion and relation decisions, release binding, canonical actor mappings, idempotent replay/conflict, stale subject revision, role mismatch, inactive membership, invalid/hidden resource/evidence, rollback, self-review rejection, append-only raw SQL protections, fail-closed behavior after privileged event/payload-binding corruption, company isolation, and API cursor pagination. Pilot fixtures are synthetic; source verification reads only the already-approved local Tanzil Q7:46 and WEBP Genesis 1:1 bytes to verify each exact selector/hash independently. Source identity is derived from validated local manifests and must match each selector.
- Actor-identity SQLite tests cover explicit active superadmin/target authorization, malformed inputs, inactive users, both collision directions, same-request exact replay, mismatched replay rejection, atomic audit creation/rollback, and append-only protection. The PostgreSQL integration test covers provisioning, request-ID conflict, audit linkage, and rollback when audit insertion fails. `scripts/run-postgres-tests.mjs` now includes this test in the dedicated integration lane.
- Isolated-schema PostgreSQL integration tests cover graph release create/read/activate/rollback and append-only graph release/record protections, plus the actual review adapter's commit/replay, verified history bindings, injected persistence-failure rollback, and append-only review-event protection. All three passed on a fresh disposable PostgreSQL 16 container on this candidate. The application database on port 5432 was not used.
- Commit `f6228f5b1bfa2e64596290d8c24328a27acfc918` adds a read-only replay-verifier hook to the workflow runtime. All existing-key paths (including unique-key race recovery) run it in a transaction; payload preparation/reducer callbacks remain skipped on replay. K3 replay, evidence resolution, and history fail closed unless the exact canonical envelope and intent bind to the terminal projection event plus workflow metadata, actor identities, company, and resource. Multi-approval intermediate events remain canonical `event:null` without a projection; timeout events are permitted only with their expected null payload and timed-out workflow state. Historical checks are company- and subject-scoped. The change is committed on `dev`; its exact-head hosted verification remains part of the current promotion candidate.
