- The blocking sentence in the section below was "no shell-capable surface beyond suggestions has adversarial negatives yet", next to a claim that the API-side suites "could not be executed in this checkout because the untracked in-flight `@moonwitness/orm-whatsapp` workspace breaks every `apps/api` vitest import". Before this change no test file in the repository mentioned `base.cron`.
- Generic surface stays closed for every role: `POST /api/base.cron`, `GET /api/base.cron` and `object.execute_kw ['base.cron','create',…]` return `403` / JSON-RPC `-32003` for a superadmin and for an ordinary user, and `canAccess` is `false` for `base.cron`, `base.job_run` and `workflow.instance` under `user`, `superadmin`, `system` and an undefined role across all five operations even when the account carries an explicit read/create/write/unlink grant for that model. `INTERNAL_PREFIXES` is evaluated before any role branch (`apps/api/src/auth/policy.ts:5,51`), and such a grant cannot even be written because `PROTECTED_ACCESS_MODELS` blocks a `base.model_access` rule targeting those models (`apps/api/src/routes/generic.routes.ts:354-364`).

- Execution boundary: an enabled, due cron naming `mw.evil.not.registered` enqueues **0** jobs; a handler registered at version 2 against a cron pinned to `handler_version` 1 enqueues **0**; the positive control with a matching registered handler enqueues exactly **1** `queued` job whose payload is byte-identical to the stored JSON while its `run` was never called during enqueue (execution counter stayed `0`). Hostile text therefore cannot reach a handler by naming it in a schedule row — only code a developer registered at the same version is ever enqueued.
- Behaviour pinned rather than idealised: `payload: null` on `POST /admin/crons` is normalised to `{}` by `body.payload ?? {}` (`apps/api/src/routes/jobs.routes.ts:289`) and accepted with `201` rather than refused. It carries no attacker-chosen bytes, so the corpus records the current contract instead of asserting a stricter one.

Two candidate repairs, both a behaviour change: validate a payload against its registered handler at create/patch time so a poison row cannot be stored, or contain the per-cron failure so one row cannot stop the rest. Neither is asserted by a test, because a passing test today would pin the bug.

## Implemented locally

- Added a suggestion-only adapter for `summary`, `term`, and `duplicate` candidate generation. It accepts bounded passage fields, copies only the explicit source/evidence/assertion allowlist, and serializes passage text as JSON data after a fixed policy that labels it untrusted evidence.
- The runtime dependency is restricted to `Pick<LocalAiRuntime, 'generate'>`; the adapter has no persistence, execution, publishing, network, or credential-reading dependency. The existing runtime itself is disabled by default and only connects to a configured loopback endpoint.
- Provider output is treated as untrusted: strict JSON parsing happens before the injected validator runs. Invalid JSON, oversized output, provider failure, or validator failure returns no candidate. The adapter returns the validator's accepted value only; persistence remains a separate K7-004 operation.
- Provider output above the 100,000-character ceiling is rejected before JSON parsing in the implementation; its regression confirms `invalid_json` and that candidate validation is not invoked.
- Context validation enforces non-empty identifiers, SHA-256 shape, passage count and text bounds, and a maximum prompt size. Extra input properties are discarded before prompt construction.
- Adversarial fixtures include attempts to override rules, execute shell commands, publish content, and reveal a credential marker. Tests confirm those strings remain JSON source data, extra properties do not enter the prompt, and no tool capability is present.
- Trusted validator and provider callbacks are captured before the provider await; a regression test mutates both caller-held properties while generation is pending and confirms only the captured callbacks run.
- API-package tests wire the adapter to `validateResearchSuggestionEnvelopeWithResolver`: unsupported injected output and an extra `execute_shell` property are rejected; an exact synthetic cited span is returned only as `unreviewed`/`INTERNAL` candidate data. The adapter is not given a persistence function.
- Added and registered `POST /api/research/suggestions/generate` with a closed request schema, endpoint rate limit, no-store response policy, active tenant evidence resolution, exact source/edition/locator/hash checks against local corpus bytes, and append-only candidate persistence. The route does not accept caller-supplied company, source text, Assertion IDs, or provider settings. The store re-resolves source and evidence through `resolverForTransaction` in the insertion transaction.
- Focused SQLite route tests cover unauthenticated access, rate limiting, malformed/extra request fields, unavailable active-tenant evidence, cross-company denial, a valid extractive candidate for both approved samples, out-of-scope model citation rejection, and company-membership revocation during provider await. The isolated-schema PostgreSQL HTTP integration also verifies unauthenticated, foreign-company, and inactive-membership denial, successful INTERNAL append-only persistence, and that membership revocation during provider generation results in a generic denial without an additional row; see [K7-004 evidence](K7-004.md).
- A route-level regression supplies an otherwise valid candidate with extra `execute_shell` and `publish` fields and an exact local citation; the API rejects it and persists zero suggestion versions.
- A combined adversarial regression feeds prompt-injection text as a trusted synthetic source passage, then returns a citation-exact candidate carrying unsupported `execute_shell` and synthetic-secret fields (`execute_shell` is set to `publish`). The trusted schema validator rejects it; the runtime surface contains only `generate`, with no persistence, shell, or publication capability.
