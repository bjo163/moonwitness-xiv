Not triggered from this audit because a dispatch is a write against shared infrastructure, and the next scheduled run is not until Tuesday 2026-10-27 04:17 UTC.
- Local reproduction remains deliberately not attempted, for the reason already recorded below: on Windows `scripts/verify-application-restore.mjs:54-58` always selects the Docker tool path, so a local run would be evidence about the wrong branch of the script.

## Deep regression incident #97 — the failing phase is measured, the message is not — `dev` `d69f661` — 2026-10-24

- The open incident issue names exactly one run: [run 39369912807](https://github.com/bjo163/moonwitness-xi/actions/runs/39369912807) on `main` at `9c9d5a3`, job `PostgreSQL upgrade, jobs recovery, and restore drill` (id 118455217387, 04:30:18Z → 04:33:22Z). Reading the job step list gives the phase: step 6 `pnpm test:integration` and step 7 `pnpm --filter @moonwitness/jobs test` **passed**, and the run reached step 9, `pnpm test:restore-drill` → [scripts/verify-application-restore.mjs](../../../scripts/verify-application-restore.mjs). So the PostgreSQL service, the required integration suite and the queue/recovery suite were all healthy; what failed is the isolated backup/restore drill itself, i.e. `createdb`, `backup-postgres.sh`, the confirmation guard in `restore-postgres.sh`, `pg_restore`, or the fixture seed/verify calls around them.
- The message is deliberately not guessed. The only annotation exposed for that check run is the generic `Process completed with exit code 1` at `.github:21`; the script's own diagnostic — which it redacts (PostgreSQL URLs, passwords, secrets) before writing to stderr — lives only in the job log, and the log could not be retrieved without authentication.
- `GET /actions/workflows/deep-regression.yml/runs` returns **one** run in total. No scheduled attempt has followed the failure, so the incident is still live; the next scheduled run is Tuesday 2026-10-27 04:17 UTC (`cron: 17 4 * * 2`). The `report-failure` / `resolve-failure` jobs are conditioned on `github.ref == 'refs/heads/main'`, so only a successful deep regression on `main` can resolve the issue — a green run on `dev` would not close it.
- Two things were not done, and why. A local reproduction on this machine would not test the failing path: `useDockerTools = process.platform === 'win32' || missingNativeTools.length > 0` makes every Windows run take the Docker-tools branch (containerised `pg_dump`/`pg_restore`, bind-mounted backup directory, `host.docker.internal` URL rewriting), while the hosted job runs on ubuntu-24.04 with native `postgresql-client-16` on the host. A green Windows drill says nothing about the Linux host branch that failed, and a red one would not identify it either. Re-running the workflow through `workflow_dispatch` was also not done: it is a shared-state action on hosted infrastructure, it consumes the runner and PostgreSQL service for up to 60 minutes, and on a `dev` ref it cannot resolve the incident anyway.
- Owner checklist for this incident: read step 9 of the failed job (needs a signed-in session or `gh run view --log`), then either fix what that message names or dispatch `deep-regression.yml` once on `main` (or on the release commit that follows) and check whether the run turns green before the 2026-10-27 schedule. Nothing in `dev` was changed to make the drill pass.

## Implemented

It starts an isolated PostgreSQL service, runs the required PostgreSQL integration suite, jobs queue/recovery tests, and isolated backup/restore drill. It scans reports before uploading a short-retention JUnit artifact.
- Existing `browser-matrix.yml` covers Chromium, Firefox, and WebKit weekly. CodeQL and Gitleaks also run weekly on separate schedules; their manual dispatch does not count as scheduled coverage.
- `platform-audit.mjs` checks the most recent scheduled run and most recent scheduled success for the browser matrix, deep regression, CodeQL, Gitleaks, and platform audit. It reports `healthy`, `failing`, `stale`, or `missing-success`; it never treats manual dispatch as schedule evidence.
- The monthly audit summary includes each scheduled workflow's status, latest successful timestamp, and freshness limit. Non-healthy schedules appear in report limitations for follow-up.
